# Angular × Browser MCP demo

Run a real Angular 22 application and both MCP packages in this extension's parent and child debug sessions. The demo is intended for local Windows use. It does not test Remote-SSH or Okta authentication.

## Try it

Run these commands from the **repository root**. Install the root dependencies with `npm ci` first.

```powershell
New-Item -ItemType Directory -Force .tmp, .cache | Out-Null
$env:TEMP = Join-Path $PWD '.tmp'
$env:TMP = $env:TEMP
$env:npm_config_cache = Join-Path $PWD '.cache\npm'
npm run demo:angular:install
npm run demo:angular
```

Chrome and a dedicated VS Code window open. The demo uses the same Chrome launch path as a normal Angular browser debug session:

1. The demo harness starts **Angular dev server** with the Node debugger and waits for `ng serve` to become ready.
2. It starts **Angular + Browser MCP**, whose target is **Angular browser**, a regular `type: "chrome"`, `request: "launch"` configuration.
3. VS Code opens `http://127.0.0.1:4201` in one dedicated Chrome with a repository-local profile.
4. Both real MCP packages connect to that same browser. The extension does not launch a second Chrome.
5. Playwright MCP toggles a task, and the harness verifies that VS Code stops at a TypeScript breakpoint in `src/main.ts` before resuming.
6. Playwright MCP performs further interactions, and Chrome DevTools MCP inspects Console and Network on the same page.
7. The windows stay open for you to try the application. The harness stops its Angular server when the parent debug session ends.

Check tasks to update the totals and progress. Add a task using the input field, or use the buttons on the right to write a Console log and send a request for local JSON. Reloading restores the initial tasks. Application state is held only in browser memory.

## Stop or check again

In VS Code, select the parent **Angular + Browser MCP** session and choose **Stop** in the debug toolbar. The Angular development server, both MCP servers, and dedicated Chrome stop. The dedicated profile is retained for the next session.

You can also stop the parent session from the repository root:

```powershell
npm run demo:angular:stop
```

This command asks the parent session to stop. VS Code launches the shared Chrome through the original browser debugger. The extension connects both MCP servers to it and coordinates cleanup.

To repeat the browser interactions, MCP checks, and screenshots while the demo is running:

```powershell
npm run demo:angular:check
```

This check reloads the page first, so tasks you added manually are reset.

## Measure memory with DevTools

While the demo is running, execute this from the repository root:

```powershell
npm run demo:angular:memory
```

The check uses Chrome DevTools MCP's `take_heapsnapshot` and `evaluate_script` tools. It captures a warm-up snapshot, a baseline, snapshots after 300 and 600 task toggles, and a final snapshot after waiting and clearing the Console. It sends 30 API requests in total and keeps the task count unchanged. Console history is cleared at the end.

The report is saved to `artifacts/angular-demo/memory/report.html`. Raw data and MCP call records are in `results.json` in the same folder. Load the `.heapsnapshot` files in the Chrome DevTools **Memory** panel and use the **Comparison** view to compare them.

Reported heap sizes are the sum of `self_size` values after garbage collection, including native nodes. They are not OS process RAM usage or snapshot file sizes. Development mode, profiling, and JIT compilation affect the results; short-term growth alone does not establish a memory leak.

## Files and ports

| Purpose | Location |
| --- | --- |
| Angular application | `http://127.0.0.1:4201` |
| Playwright MCP | `http://127.0.0.1:8931/mcp` |
| DevTools MCP tools gateway | `http://127.0.0.1:8932/mcp` |
| Dedicated Chrome CDP | Automatically assigned local port |
| Screenshots and MCP verification results | `artifacts/angular-demo/` |
| Dedicated profiles, startup logs, and state | `.tmp/angular-demo/` |
| npm and Angular caches | `.cache/` |

Startup is refused if any of the three fixed ports is in use. Existing port owners are left running. The demo uses a separate Chrome profile and does not inherit your usual Chrome login state.

To use different executable locations, set `browser.executablePath` in the sample launch configuration and `BROWSER_MCP_CODE_EXECUTABLE` in your environment to their absolute paths. Depending on your environment, the windows may open behind other windows; select them from the taskbar.

## Start manually from VS Code

1. Install the VSIX generated by `npm run package` on the local side of VS Code.
2. Install Chrome. No browser extension or manual remote debugging setup is needed for dedicated Chrome.
3. Open this `samples/angular-demo` folder in VS Code.
4. In **Run and Debug**, start **Angular dev server** and wait for the server to be ready.
5. Select **Angular + Browser MCP** and choose **Start Debugging**. Stop the separately started dev-server session when finished.

The `.vscode/launch.json` configuration wraps **Angular browser** through `browser-mcp`. Angular component TypeScript breakpoints and both MCP servers use the same Chrome. In your own project, keep your existing Chrome target's startup and cleanup tasks; those tasks are preserved.

To view the application without MCP, run `npm start` in this folder. Run `npm run build` to check the production build.

Versions are pinned to Angular 22.2.5, CLI/build 22.2.6, Playwright MCP 0.0.85, and Chrome DevTools MCP 1.12.0. See the [official Angular compatibility table](https://angular.dev/reference/versions) for Node.js requirements. This demo was tested with Node.js 22.23.4.
